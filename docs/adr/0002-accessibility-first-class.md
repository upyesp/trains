# Accessibility is a first-class requirement

The site is built for two co-equal audiences: sighted users and **screen-reader users** (blind / low-vision). Accessibility is a founding constraint, not a polish step — every design and build decision is evaluated against it from the start, because retrofitting accessibility onto a finished UI is far harder and ships exclusionary software in the meantime. Target conformance: **WCAG 2.2 Level AA**, with AAA pursued opportunistically where it's free.

## Consequences

- **Screen-reader users are a primary audience, not an edge case.** The Board must be a semantic structure (a real `<table>` with proper headers, or a labelled list), fully keyboard-operable, with landmarks, a skip link, and a logical reading/focus order.
- **State is never conveyed by visual styling alone** (colour, weight, size). The canonical case — raised explicitly — is the platform: a **provisional** vs **confirmed** platform must carry that state as *text/semantics* (an accessible name) in addition to any visual treatment. Same rule for delay status, cancellations, on-time: never colour-only. This is the deliberate alternative to RTT's own site, which encodes confirmed-platform as bold weight (invisible to screen readers).
- **Live-updating content uses `aria-live` discipline — announce meaningful changes only.** A Board that refreshes every 30s must **not** interrupt screen-reader users every 30s. Policy (resolved): routine refreshes are **silent**; a polite `aria-live` region surfaces only *actionable* events — a **cancellation**, a **platform change**, or a **significant delay swing** (≈ ≥5 min). The Board structure itself is read as a unit between changes. Exact ARIA markup is design-time; the *policy* is fixed. Architectural consequence: the system must **diff the previous board against the fresh one and classify deltas** — a small component that composes naturally with the caching layer, which already holds the previous board.
- **Testing is planned, not optional:** automated (Lighthouse / axe-core) plus manual keyboard and screen-reader testing (NVDA / VoiceOver) before launch, per the accessibility skill's checklist.
- The **accessibility** skill is re-invoked for a full audit once a UI exists; the **frontend-design** skill is engaged alongside it so "modern and amazing" and "accessible" are solved together, never traded off against each other.
